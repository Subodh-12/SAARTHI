1. Purpose, rules and maturity
This is the single source of truth for building SAARTHI. Every teammate and every coding
agent works from it, and a decision made here is binding until someone edits it here.

Page 2 of 57

SAARTHI — Design Document v2

Product in one sentence: SAARTHI is a stateful learning agent that decides a Class 9
Odia-medium learner's next educational action from what they know, what they need and
what the device can currently do, and keeps working when the network drops.
Maturity statement (Decided). SAARTHI is built with production engineering practice,
but until reliability, privacy, security, Odia quality and target-device performance have
each been verified by the tests in Section 15, it is described as a production-minded,
offline-first MVP. The design specifying backups, monitoring, TLS and retries does not
make it production-ready; running the operational tests and publishing the results does.
Rules for humans and coding agents
Build only what this document specifies. If a detail is missing, pick the stated default,
record it in docs/decisions.md , and add it to Section 18.
The rule engine chooses the learning action. The LLM writes words and never picks the
action (Section 4).
Offline is the default path, not an error path. Every feature ships with its offline
behaviour defined and tested.
Every tool and provider call returns a typed result or a typed error. No unhandled
exception crosses a service boundary.
Compute is stateless; correctness never depends on process memory (Section 5).
Contracts are generated: Pydantic models are the source, OpenAPI and TypeScript
types are generated from them. Never hand-edit generated types, and never change a
contract in only one service.
A feature is done only when it meets the Definition of Done in Section 16, which
requires verified behaviour, not a component that merely starts.
All learner-facing text is Odia-first. English strings are developer fallbacks only.
Instructions to a coding agent: read Sections 1 to 9 and Appendix A fully before writing
code, implement in the milestone order of Section 16, and after each milestone run the
tests of Section 15 and report results against that milestone's gate.
Labels used: Decided means build it this way. Default means build it this way unless the
owner changes it. Open means unresolved and tracked in Section 18.

packs, reliable sync.

other subjects and languages, native Android app, on-device language models, teacher

Non-goal: SAARTHI is not a general chatbot. Off-curriculum questions are politely
redirected, not answered freely.

4. Agentic approach
Decision (Decided): a deterministic workflow agent built as a LangGraph state machine,
with bounded autonomy inside two nodes. The graph chooses the learning action by
explicit rules over learner state and environment state. The LLM generates explanations
and practice questions inside nodes and never chooses the action.
Why deterministic at the core
The next action must be explainable to a judge, a teacher and a parent. Rules over
mastery and connectivity are auditable; a free-running LLM planner is not.
The same decision must run on the phone with no network. A rule engine fits in a few
kilobytes of JavaScript; an autonomous planner needs a hosted model.

LLM output in Odia is uneven in quality. Keeping the model out of control flow limits a

Framework (Decided): LangGraph on the server for orchestration, with checkpoints in
PostgreSQL. A TypeScript implementation of the decision subgraph (pure functions, no
LLM, no network) runs on the client. Both load the same versioned rules.json and must
pass the same test vectors, so the two cannot silently disagree.
LLM provider policy (Decided): the generator sits behind the provider interface of

in the core decision loop, and the local rule fallback always remains.

The phone can make every learning decision alone. The cloud adds heavier AI and the
reconciled record, using stateless processes over durable stores.

The phone owns events until the server acknowledges them. After sync, the server owns
the reconciled, authoritative state. AI providers and generators never write to a database;
they return typed results to the router.
Transaction boundary for ingestion (Decided). One database transaction inserts the
batch of events (idempotent on device_id and seq), applies accepted events to the
mastery projection in canonical order, and advances the device cursor. The server
decision is computed after that commit, so a decision failure never rolls back accepted
events. If the decision cannot be computed, the response says so and the phone keeps its
local decision.

Before a decision is saved or shown, it must pass the trajectory check: the target concept
exists, the action and reason code are in their enums, the delivery mode is feasible for the
installed packs and network state, and the ruleset version is known. A failing decision is
replaced by the fallback decision (reason STATE_INVALID_FALLBACK) and logged at high
severity.
Normalised input and mastery representation (Decided). Mastery is stored and
compared as integer basis points (0 to 10000), so Python and TypeScript cannot disagree
through floating-point rounding. Concept lists are sorted by concept ID, timestamps are
not inputs to the planner, and the environment snapshot is reduced to the network state,
free-storage bucket and installed pack versions.

Bayesian Knowledge Tracing update (Decided). For a graded answer on a concept with
stored mastery p (basis points divided by 10000, or p_init if the concept is new): if
correct, posterior = p(1 - slip) / (p(1 - slip) + (1 - p) guess); if wrong, posterior = p slip / (p
slip + (1 - p)(1 - guess)). Then p_next = posterior + (1 - posterior) learn, clamped to 0.01 to
0.99, and stored as basis points rounded half up. Each update starts from the stored
integer, so replay is exact. Parameters live in rules.json under a bkt_version ; changing
them bumps the version and forces a full projection rebuild by replay.
Learning-action rules (Decided). T is the target concept. Thresholds are in basis points in
rules.json. The first matching rule wins.

9. Offline-first client, event ordering and replay
Principle (Decided). The phone is authoritative for what the learner just did; the server is
authoritative for the reconciled state. Learner actions are appended as immutable events
and mastery is derived from them, so sync merges event logs and never has to merge
conflicting values.
Client architecture
React PWA built with Vite and TypeScript, installable, with a Workbox service worker.
App shell and installed packs are cache-first. API calls are network-first with a 6 s
timeout, then fall back to local logic.
All state changes go through the ProfileSession store module, which writes the
state change and its outbox event in a single IndexedDB transaction, so one can never
exist without the other.
A NetworkMonitor produces the network state of Section 10.
Storage guard: request persistent storage at first run, warn at 50 MB free, never evict
an installed pack without the learner's consent.
Canonical event ordering (Decided). Bayesian Knowledge Tracing is sequential, so the
order of answer events changes the result and must be fully defined.

Replay invariant (Decided). Replaying the same accepted event log in canonical order

Sync protocol (Decided)
1. Trigger: the network becomes online or usable-weak, the app returns to the
foreground, or 5 minutes pass during an online session. Before syncing, auth is
renewed if needed (Section 8).
2. For one profile at a time, the phone sends its oldest 100 outbox events in seq order
with the environment snapshot to POST /sync .
3. The server validates and, in one transaction, inserts the events, applies accepted ones
to the projection in canonical order and advances the cursor. It returns a result per
event.
4. After commit the server computes a decision and returns it with authoritative mastery
and any pack updates.
5. The phone applies the outcome rules of Section 8, replaces local mastery with the
server's, then re-applies its own events created after the upload, in seq order, with the
same update function (rebase).
6. If outbox events remain, repeat from step 2. A partial failure leaves unacknowledged
events untouched.
7. If the server decision conflicts with what the learner is currently doing, it is stored as a
pending suggestion and shown at the next natural break (Section 10).

11. Content and RAG pipeline
Content quality decides whether learners and teachers trust the product, so content is a
managed pipeline with human review and a publication gate. The MVP covers three Class
9 Science chapters end to end.
End-to-end flow (Decided)

Page 34 of 57

SAARTHI — Design Document v2

1. Source material and rights check. Confirm permission to use and redistribute each
source before it enters the pipeline (Section 18, D1). No pack is published without it.
2. Extraction. Copy text from digital sources, or OCR scanned pages and correct by hand.
3. Odia normalisation. Unicode NFC, layout artefacts removed, digit forms recorded.
4. Concept and prerequisite tagging. A subject expert and the Odia lead split each
chapter into concepts with stable slug IDs and prerequisite links.
5. Chunking and glossary. 80 to 200 Odia words per chunk, one idea each, with concept
ID, textbook page reference and glossary terms. The glossary maps technical terms
between Odia and English.
6. Question bank. At least 12 questions per concept (4 per difficulty), each with an
answer key and a misconception tag on every wrong option. LLM drafts are allowed,
but every item is reviewed by a human before entering the bank.
7. Indexes. Dense embeddings and a keyword index for the server; a compact keyword
index built on the phone at install time.
8. Pack build. Write the pack files of Section 7, compute checksums, store under a
temporary key.
9. Publication gate. The pack is promoted and listed in the manifest only if every check
below passes.
10. Device installation. The phone downloads in resumable parts, verifies the checksum,
installs, builds its local index, and records PACK_INSTALLED.
Publication gate (Decided). A pack is not published, and the job goes to dead with a
visible reason, if any of these fail:
Every required Odia field is present and non-empty.
Every chunk has a valid concept link and a page reference; every concept's
prerequisites exist and the graph has no cycle.
Every question has an answer key, a revision number and a misconception tag on each
wrong option.
Citations and chunk IDs resolve; glossary terms referenced in chunks exist.
Total size is within the budget measured in Section 15, and the checksum verifies after
upload.
Versions and stability. Concept and question IDs never change. A reworded question or
changed key becomes a new revision; the old revision is marked legacy only after every
supported app version has stopped serving it. Old packs remain usable offline, and the
server interprets old events through the revision recorded in each event (Section 6).

SAARTHI — Design Document v2

Server retrieval (Decided): hybrid
The query is normalised, and English technical terms are expanded through the
glossary to their Odia forms and the reverse.
Dense and keyword search each return the top 8; reciprocal rank fusion merges them
and the top 4 chunks go to the generator.
The embedding model is chosen by measurement: compare at least two multilingual
models on 100 labelled Odia queries by recall at 5 and record the choice in Section 18.
If the best score is below the threshold set from that evaluation, the agent does not
answer from the model's own knowledge. It says the topic is outside the current
lessons and offers the nearest concept.
Local retrieval on the phone (Decided). BM25 keyword ranking over the pack's Odia
index plus glossary expansion. The answer is extractive: the best chunk, the key sentence
highlighted, and a link to the related concept. No model is needed offline.
Grounding rule. Every generated factual answer must cite at least one chunk ID and the
chapter reference. Section 13 defines the checks that enforce it.

12. Odia language and voice strategy
The language bonus is judged on whether the experience feels native, not on translated
labels. Odia is a first-class requirement in every layer, owned by the Odia, assessment and
evaluation lead.
What makes it native (Decided)
Interface text written by a native speaker, not machine-translated: short sentences,
everyday words, no jargon in navigation.
Technical terms shown as learners meet them in class: the Odia term with the English
term in brackets, driven by the glossary.
Code-mixed input is expected: Odia script, Odia written in Latin letters, and Odia with
English terms. The query normaliser handles all three.
Answers use the register of a Class 9 textbook explanation, with one everyday
example where the chunk allows.
A bundled Odia font subset (for example Noto Sans Oriya) ships in the app shell,
because low-end phones often render Odia badly.
Odia and Latin numerals are both accepted in input; display follows a learner setting.

An engine that always returns a valid action can score 100% on validity while choosing
poor interventions, which is why quality is measured separately against expected actions.
Decision-quality gold set (Decided). At least 120 scenarios, each a normalised state and
environment, labelled with the expected learning action and reason by two people who
did not write the rules (the subject expert and the Odia lead), with disagreements
resolved by discussion and recorded. At least 30% are held out and not used while tuning
thresholds. Required coverage: prerequisite gaps, repeated wrong answers, no progress
after remediation, mastered concepts, slice complete, missing pack while offline, low
storage, weak network, cold start, and corrupt or stale state. Disagreements between the
engine and the labels are investigated as either a rule fault or a labelling fault; thresholds
are not tuned until the set merely passes.

You are building SAARTHI as a production-minded MVP, following the attached
design document exactly.
1. Read Sections 1 to 9 and Appendix A before writing code.
2. Work in the milestone order of Section 16, one milestone per branch, and
stop at each gate to run the tests of Section 15 and report pass or fail.
3. Create the repository layout of Section 14. Define the Pydantic contracts
first and generate OpenAPI and TypeScript types from them. Never hand-edit
generated types.
4. Implement the decision engine as pure functions in Python and TypeScript,
both reading rules.json, storing mastery as integer basis points, and passing
the same test vectors, including invalid input.
5. Never let an LLM choose the learning action. Never call the network or an
LLM from the local engine.
6. Every tool and provider call returns a typed result or a typed error
(Section 5). Providers never write to a database.
7. Events are written with their state change in one local transaction. Sync
returns one outcome per event; remove an event from the outbox only on
ACCEPTED, DUPLICATE or after moving it to quarantine.
8. Keep profile data isolated through one ProfileSession module. Do not cache
API responses that contain learner data.
9. Generated answers pass the ordered validation contract of Section 13; if
grounding cannot be verified, show a labelled extractive answer or redirect.
10. If the document is silent, take the stated default, record it in
docs/decisions.md, and continue. Do not add features outside Section 2 or
infrastructure outside Section 14.
11. Report what you verified and what you did not. Do not describe the system
as production-ready.

The human owners keep the content, model and voice decisions of Sections 11 and 12,
because they depend on measurement and Odia review, not on code.
